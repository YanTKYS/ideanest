# 設計判断

このドキュメントは「なぜこの形にしたか」を残すためのものです。
迷ったら、ここを参照して再判断します。

## なぜカード型 UI にしたか

- 想定するユースケースが「思いつき」「断片」「短文」だから。
- ツリーやアウトラインだと、書く前に **場所を選ぶ判断** が発生してしまう。
  これがアイデアを書き始める初動を遅らせる、というのが NoteNest を運用してきた実感。
- カードの一覧であれば、「とりあえず追加 → あとで探す」が成立する。
- Google Keep のメンタルモデルが広く受け入れられており、初見ユーザーが説明なしで使える。
- ただし Keep の忠実コピーは目指さない。ローカルで完結すること、`.ideanest` 1 ファイルで持ち運べることを優先する。

## なぜ単一 JSON ファイルにしたか

- ユーザーが **自分のファイルとして所有できる** こと、を最も大事にしたい。
- SQLite やキャッシュフォルダだと「アプリが管理する不透明な箱」になり、
  バックアップ・共有・移行が一般職員には難しくなる。
- JSON なら最悪テキストエディタでも読める。これは長期保管にとって重要な特性。
- v0.1.0 は規模が小さい (アイデア数 ≲ 数千) ことを想定しているので、
  JSON 1 ファイルでパフォーマンス上の問題は出ないと判断した。
- バイナリ依存を避けることで、`.bak` による単純な復旧戦略も成立する。

## なぜ画像貼り付けを対象外にしたか

- 単一 JSON ファイルという設計を最優先にした結果、
  バイナリ添付を抱えると JSON が肥大化するか、外部フォルダ参照が必要になる。
- どちらに倒しても「単一ファイルで持ち運べる」が崩れる。
- v0.1.0 の主目的は「素早くテキストを溜める」であり、画像なしで成立する。
- 画像が必要な人は NoteNest 側で扱う前提とする (将来検討)。

## なぜタスク管理を対象外にしたか

- IdeaNest を「期限を持つ仕事の管理」に使い始めると、すぐに NoteNest と機能が重なる。
- 期限・進捗・担当者などを追加した瞬間に **書く前の判断コスト** が増え、
  「思いつきを雑に溜める」というコンセプトが壊れる。
- 期日管理は NoteNest あるいは既存のタスクツールで行う、と境界を明確にした。
- IdeaNest 側は、あくまで「思考の在庫」までを担当する。

## なぜ画面を「カード一覧主役」にしたか (v0.1.2)

- IdeaNest の役割は「思いつきを溜める箱」であり、ユーザーが画面を開いて最初に
  見るべきものは **過去に溜めたカードの一覧** である。
- NoteNest のような「プロジェクト × ツリー × エディタ」型は構造化に強いが、
  カードの俯瞰には不向きで、視線が左ペインや上部メニューに分散する。
- IdeaNest ではカード以外の UI 要素 (枠線・濃いボタン・標準コンボボックスなど)
  をできる限り後退させ、カードを浮き上がらせる構成を取る。
- このため背景を薄いグレー (`#F6F7F9`)、カードを白 + 角丸 + 薄い影で表現し、
  「Google Keep のような軽いボード」というメンタルモデルを優先する。
- ただし Google Keep の見た目を忠実にコピーするわけではない。
  ローカル単一ファイルで完結することを最優先にした上で、その範囲で軽く整える。

## なぜ外部 UI ライブラリを導入しないか (v0.1.2)

- MahApps.Metro / Material Design In XAML / Fluent UI ライブラリなどを入れれば
  見た目は一気に「今っぽく」なるが、依存と学習コストが大きく増える。
- IdeaNest はプロトタイプ規模であり、UI 周りの依存は最小限にしておきたい。
- DLL が増えると自己完結型 (`PublishSingleFile=true`) でも配布物が肥大化する。
- 「カード型ボード」というシンプルな構造であれば、WPF 標準の `Border` /
  `DropShadowEffect` / `ControlTemplate` だけでも、業務画面感を十分に取り除ける。
- 装飾の自由度より、**起動 → 追加 → 検索 → 保存** の素直さを保つことを優先する。

## なぜ機能追加より見た目の整理を優先したか (v0.1.2)

- v0.1.0 / v0.1.1 で「起動 → 追加 → 検索 → 保存 → 読込」の機能は揃った。
- 一方で UI の野暮ったさが、アイデアを見返す体験を阻害していた
  (枠線が多い / カードが平らで読み返したくならない / ボタンが業務画面的)。
- カード型ツールにとっては **「もう一度開きたくなる見た目」** が機能と同じくらい
  重要であり、ここを先に整えないと機能を追加しても使われない。
- そのため v0.1.2 では、機能追加・データ構造変更・保存形式変更は一切行わず、
  視認性と落ち着きだけを底上げした。

## タグ設計の方針 (v0.2.0)

### タグをカードから算出する構造にした理由

タグを独立した DB テーブルや別リストとして管理せず、カードの `Tags` リストから都度算出する設計を採用している。

- `.ideanest` を 1 ファイルで完結させる方針 (タグマスタを別コレクションに持つと JSON 構造が複雑になる)
- カードを削除・編集すれば自動的にタグ一覧が更新される (使われていないタグは自然に消える)
- 将来 v0.x.y で算出コストが問題になる規模 (タグ数 × カード数 が数万) に達した場合はキャッシュ化を検討するが、
  当面は不要と判断した

この設計のため、「未使用タグのクリーンアップ」という操作は不要 — 単純にカードからタグを消せばよい。

### タグ正規化の範囲を最小限にした理由

v0.2.0 でのタグ正規化は「前後空白除去」「先頭 `#` 除去」「空タグ除外」「同一カード内重複排除」のみに留める。

- 大文字小文字の正規化 (`UI` と `ui` を同一視) や全角半角統一は、ユーザーが意図的に使い分けている可能性がある
- v0.1.x 以前のデータを静かに書き換えることへのリスクを避けたい
- 正規化規則が増えると「なぜこのタグが消えたか」がわかりにくくなる

意図した区別が必要な場合は、タグ管理ダイアログでリネームして明示的に統合できる。

この方針に合わせ、タグ一覧の算出 (`RefreshTags`)・タグ絞り込み・タグのリネーム・削除
は すべて `StringComparer.Ordinal` / `StringComparison.Ordinal` で比較する。
`UI` と `ui` は別タグとして扱われ、左ペインにも別行で並ぶ。
一方、検索欄からのキーワード検索 (タイトル / 本文 / タグへの部分一致) は
ユーザーの利便性のため `OrdinalIgnoreCase` のままにしている。
これはタグの同一性判定ではなく、検索ヒットの寛容さなので別ルールで構わない、と判断した。

### タグリネーム = マージとした理由

「リネーム」と「マージ」を別機能として実装する案もあったが、
「リネーム先に既存タグ名を指定したら統合」という 1 つの操作に統一した。

- 操作フローが 1 種類で済む (UI 項目が増えない)
- 「同じ概念を表す 2 つのタグを 1 つにまとめたい」という需要はリネームと本質的に同じ
- タグ管理ダイアログに「マージ先を指定する複数選択 UI」を持つのは v0.2.0 の規模では過剰

## v0.2.3 でクリップボードコピーに Ctrl+C を使わなかった理由

- 現状の実装には「選択中カード」という UI 概念が無い。
  `Ctrl+C` を Window レベルで捕まえると、
  検索欄や他のテキストボックスの通常コピー操作と衝突する。
- `Ctrl+Shift+C` を「表示中カードの一括コピー」に割り当てることで、
  既存ショートカットと衝突せず、意図が明確な操作として機能する。
- カード単体コピーは右クリックメニューで提供し、
  キーボード派には一括コピーショートカットを用意するという分担にした。
- 将来カード選択モデル (クリックで選択状態 + `Ctrl+C` コピー) を導入する場合は、
  `backlog.md` のカード選択モデルと合わせて改めて設計する。

## v0.2.3 の Markdown 整形ロジック共通化について

- v0.2.2 では `MarkdownExportService.Export()` が整形とファイル書き出しを一体で行っていた。
- v0.2.3 では `FormatCard()` (単一カード) と `FormatAll()` (ヘッダー + 全カード) を分離し、
  `Export()` は `FormatAll()` を呼んでファイルに書くだけにした。
- クリップボードコピーはこれらのメソッドを直接呼び出すため、
  出力フォーマットがファイルエクスポートと一致することを保証できる。
- 過度な抽象化を避けるため、テンプレートエンジンや設定可能なフォーマット等は導入しない。

## v0.2.2 で NoteNest 専用連携より汎用 Markdown エクスポートを先に実装した理由

- IdeaNest に溜めたアイデアの活用先は NoteNest に限らない。
  Markdown エディタ・記事下書き・設計メモ・プロンプト作成など多様であり、
  最初から NoteNest 専用フォーマットに縛ると汎用性が失われる。
- `.ideanest` は「ローカルで所有・保管するデータ形式」、
  Markdown エクスポートは「外部ツールで活用するための書き出し」と役割を分ける。
  両者は独立しており、エクスポートが `.ideanest` の構造に影響しない。
- 再インポート (`.md` → `.ideanest`) は v0.2.2 の対象外。
  IdeaNest の役割は「思考の在庫」であり、
  インポート機能が必要になるのは別ツールとの連携フローが確立してからでよい。
- NoteNest 向けエクスポートは将来 v0.3.0 以降で個別に検討する。
  Markdown エクスポートで共通部分 (フィルタ反映・UTF-8・出力順) の設計を先に固める。

## なぜ NoteNest とは別ツールにしたか

- 同じアプリの中に「腰を据えて書く画面」と「雑に溜める画面」を同居させると、
  どちらの UI も中途半端になりやすい。
- 起動時にモード選択を強いるのも、初動コストを上げてしまう。
- 別アプリにすることで、ショートカット起動でそれぞれを最短距離で使える。
- データも `.notenest` / `.ideanest` で完全に分離でき、
  片方が壊れてももう片方に波及しない。
- 将来 NoteNest 向けエクスポートを足すとしても、それは橋渡しであり同居ではない。
