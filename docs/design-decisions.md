# 設計判断

このドキュメントは「なぜこの形にしたか」を残すためのものです。
迷ったら、ここを参照して再判断します。

## MainViewModel の段階的分割方針 (v0.8.1 〜)

### 背景と方針

`MainViewModel` は v0.7.x までにアプリ全体の状態・コマンドを集約しており、
1000 行を超えていた。全面分割は影響範囲が大きいため、以下の方針で段階的に進める。

1. **WPF 非依存な責務から切り出す** — `System.Windows` を import しないサブ ViewModel は
   `IdeaNest.Tests` に `<Compile Include>` で追加でき、クロスプラットフォームで
   単体テストを書ける。これが安全網として機能する。
2. **コールバック渡しで疎結合を保つ** — サブ ViewModel はコンストラクタで
   `Action onRefreshVisible` / `Action onMarkDirty` を受け取り、
   WPF や `MainViewModel` の具体的な型を知らなくて済む。
3. **XAML バインディングを変えない** — `MainViewModel` は薄い転送プロパティを残し、
   `CardDisplay.PropertyChanged` を `MainViewModel.PropertyChanged` として再発火する。
   これにより `{Binding CardWidth}` 等の既存 XAML を無変更で維持できる。
4. **一度に 1 〜 2 責務を切り出す** — 大規模リファクタリングは避け、
   既存テストが全件グリーンであることを確認しながら進める。

### 今後の候補 (backlog M12 で継続)

現時点で WPF 非依存に切り出せる純粋ロジックの主要な塊は出尽くしている。
今後の分割対象としては、`RefreshVisible` の絞り込み・ソート段 (CardDisplay の `OrderByShuffle` と
`Filter.*` を組み合わせた純関数として抽出可能) や、自動保存スケジューラ (DispatcherTimer 起動条件
の集約) が候補だが、いずれも v0.8.x の範囲では現状の構成で機能しているため後続で再検討する。

### v0.8.4 で `IExportPlatform` インターフェースを導入した理由

- v0.8.1 〜 v0.8.3 のサブ ViewModel はコールバック (`Action onMarkDirty` 等) で
  WPF 依存を逃がしてきた。
- 一方で v0.8.4 のエクスポート責務には WPF タッチポイントが 5 つある
  (`SaveFileDialog` / オプションダイアログ / `Clipboard` / 情報ダイアログ / エラーダイアログ)。
  これらをすべて個別の `Func` / `Action` で受けると、コンストラクタが煩雑になり
  意味のあるグルーピングも失われる。
- そこで `IExportPlatform` という 5 メソッドの薄いインターフェースに集約した。
  `ExportViewModel` 本体は WPF 非依存のまま、テスト時はモックを差し替えるだけで
  ファイル書き込み / クリップボード / ダイアログのすべてを観測できる。
- 本体 (WPF) 側は `WpfExportPlatform` 1 ファイルにまとめ、
  `SaveFileDialog` のフィルタ文字列・既定拡張子といった UI 詳細を MainViewModel から退避。
  これらの WPF 詳細は今後 UI を別 OS に移植する際の単一の隔離ポイントになる。
- DI コンテナ導入は引き続き対象外。インスタンスは MainViewModel が `new` で生成する。

### v1.0.0 を「機能凍結された正式リリース」と位置付けた理由

- v0.9.0 までで、コアとなる「素早く溜める / あとから探す / NoteNest と棲み分ける」
  というコンセプトが満たされ、`MainViewModel` の責務分割と単体テスト (304 件) も
  ひと区切りついた。これ以上の v0.x 系での積み増しは、機能停滞よりも
  「**安定動作する v1.0.0 として配布できる状態**」を作ることに価値がある段階。
- v1.0.0 自体の差分は限定的: csproj `<Version>` を `1.0.0` に上げ、README とドキュメント
  上の表記を整える。コードの動作は v0.9.0 と等価。これは v1.0.0 を機能リリースではなく
  「正式リリース版の表明」として扱う設計判断による。
- 新機能・大規模リファクタは v1.0.0 後に再開する。`docs/backlog.md` の
  「v1.0.0 以降に検討」セクションがその出発点になる。
- `Assets/tutorial.png` のような Windows ビルド時にのみ顕在化する問題は、
  本リポジトリの管理外 (実機ビルド側) で確認する責務として `docs/test-scenarios.md` の
  リリース前チェックリストに切り出した。v1.0.0 リリースノートにも明記している。

### v0.9.0 で総点検を行った理由 (v1.0.0 への準備)

- v0.8.1 〜 v0.8.9 で `MainViewModel` の分割を 9 段階に分けて進めた結果、WPF 非依存の純粋
  ロジックは出尽くした。それ以上の分割は得るものが少なく、むしろ呼び出し階層を深くするため
  ここでひと区切りとした。
- v0.9.0 では新機能を一切追加せず、リファクタ後の不整合 (リリースノートのテスト件数、
  test-scenarios.md の UT 一覧、backlog の完了済み項目) をドキュメント側で揃え、
  v1.0.0 (機能凍結 / 配布準備) に進める判断材料を作った。
- `docs/backlog.md` に「完了済み / v1.0.0 前 / v1.0.0 後」のスコープ区分を導入した。
  M12 (MainViewModel の段階的分割) を「完了済み」へ移動し、新機能要素を含む既存項目は
  すべて「v1.0.0 後」に整理した。これにより v1.0.0 までに何をやり残しているか
  (現時点では v1.0.0 前の項目は配布準備のみ) が一覧で見える。

### v0.9.0 で `*Service` クラスの配置を移動しなかった理由

- v0.8.8 / v0.8.9 で追加した `CardOperationsService` / `TagSyncService` / `TagManagementService`
  はクラス名が `*Service` でありながらソース上は `src/IdeaNest/ViewModels/` 配下に
  `namespace IdeaNest.ViewModels` として配置されている。
- v0.9.0 の総点検では配置移動を見送った。理由は次のとおり:
  - 動作変更を伴わない純粋な整理だが、3 ファイルの移動 + namespace 変更 + テストプロジェクトの
    `<Compile Include>` パス更新 + 呼び出し側の `using` 追加が一括で必要になり、
    v0.9.0 の「小修正と回帰確認に留める」方針からは外れる
  - 既存のテスト 304 件はクラス名で参照しており、namespace 変更でも全件影響を受ける
  - v1.0.0 で配布物を固める前に整理する価値はあるが、v1.0.0 のリリースを止めるほどの
    重要度ではない
- backlog に `M14` として v1.0.0 後の候補に明示的に残した。`Services/` への
  移動と同時に、フォルダ命名規約 (Services は静的・状態を持たない計算、ViewModels は
  `INotifyPropertyChanged` を伴う UI 状態) を design-decisions.md で言語化する案も
  あわせて検討する。

### v0.8.9 でタグ管理ロジックを TagManagementService に切り出した理由

- v0.8.8 までで `MainViewModel` から純粋ロジックの大半を切り出した結果、残っていたのは
  `RenameTag` / `DeleteTag` の本体 (約 50 行) だけだった。これらは
  「全カード走査 → タグ書き換え → `Touch` / `OnExternalUpdate` → 選択タグ調整 → dirty / refresh」
  という完全に決まったパイプラインで、WPF にも `_workspace` にも触らない。
- 切り出し先を「Service」にした理由は、`CardOperationsService` と並びを揃え、
  状態 (タグ一覧自体) は持たず、コールバックでのみ外部と接続する構造に統一するため。
  `TagManagementViewModel` 名は採用しなかった: タグ管理ダイアログ自体の状態
  (検索文字列・並び順など) はまだ追加していないため「ViewModel」と呼ぶには内容が薄い。
- 既存の `TagManagementWindow.xaml.cs` は `_vm.RenameTag(...)` / `_vm.DeleteTag(...)` の形で
  呼び出していたため、`MainViewModel` 側に同名の薄いメソッドを残してダイアログ側のコードは
  無変更を維持した。XAML / コードビハインドへの波及をゼロにする方針は v0.8.1 以降一貫している。
- 「リネーム = マージ」の挙動は v0.2.0 で確立した設計判断であり、これを内部で別経路にせず、
  `WorkspaceService.NormalizeTags` の重複畳み込みで自然に成立させる構造を維持した。
  「マージは rename の特殊ケース」という構造的事実をコードに残したい。
- 選択タグ追従 (`SelectedTag` がリネーム対象なら新名に追従 / 削除対象ならクリア) は、
  `Func<string>` / `Action<string>` で外から差し込める形にした。
  これにより `FilterViewModel.SelectedTag` の更新をプロパティ経由で確実に通すことができ、
  サービス側は `FilterViewModel` の実装詳細を知らずに済む。
- `_tagMgmt` は `AllCards` と `SelectedTag` のゲッタ/セッタ越しに状態を見るため、
  ワークスペース入れ替え時の再生成は不要 (`CardOperationsService` が `_workspace.Ideas` を
  直接参照するため再生成が必要だったのとは対称的)。
- DI コンテナは引き続き対象外。`_tagMgmt` は `MainViewModel` のコンストラクタで `new` する。

### v0.8.8 でカード操作・タグ集計を 2 クラスに切り出した理由

- v0.8.7 の回帰確認後、`MainViewModel` にはまだカード CRUD とタグ集計の 200 行ほどが残っていた。
  これらはいずれも WPF に依存しない純粋なロジックで、これまでと同じ方針 (コールバック渡し) で
  切り出せる対象だった。
- `CardOperationsService` をインスタンスクラスにした理由は、コンストラクタで
  `List<Idea>` / `ObservableCollection<IdeaCardViewModel>` / 3 つのコールバック /
  `Func<DateTime>` を受け取ることで、テスト時に状態変化をすべて外から観察できるから。
  静的クラスにするとパラメータが長大になるか、テストごとの独立性が失われる。
- `Func<DateTime>` を差し込んだのは `CommitAdd` のタイムスタンプを決定論的にテストするため。
  `card.Touch()` (`CommitEdit` / `TogglePin` / `ToggleArchive`) は `DateTime.Now` のままとし、
  テストでは「before ≤ card.UpdatedAt ≤ after」でバウンド検証する。
- `_cardOps` は `ReloadFromWorkspace()` の先頭で再生成する。`_workspace` が差し替わる
  (`NewWorkspace` / `Open` / `LoadStartup`) 経路はすべて `ReloadFromWorkspace` を経由するため、
  `_workspace.Ideas` への参照が陳腐化しない。
- `TagSyncService` を静的クラスにした理由は、状態を持たない純関数 (入力: カード一覧、出力: タグ一覧)
  であり、インスタンスにすると依存が増えるだけで利点がないから。
- `RefreshTags` が `MainViewModel` に残っている理由は、`AvailableTags` (ObservableCollection) と
  `TagPanel.SetAllItems` の両方を更新する責務であり、どちらも WPF / ViewModel の状態に属するため。
  集計ロジックだけを `TagSyncService` に移し、書き込み側は `MainViewModel` が担う分担とした。
- DI コンテナは引き続き対象外。`_cardOps` は `CreateCardOps()` ヘルパーで `new` する。

### v0.8.6 で保存状態・自動保存まわりを SaveStateViewModel に切り出した理由

- `MainViewModel` に残っていた 5 つのフィールド (`_currentFilePath` / `_isDirty` /
  `_isAutoSaving` / `_autoSaveFailed` / `_lastAutoSaveTime`) と、それらに依存する
  `SaveStatusText` 文言生成はすべて純粋なロジックであり、WPF に依存しない。
- これらを 1 つのクラス (`SaveStateViewModel`) に集め、明示的な遷移メソッド
  (`MarkDirty` / `OnFileLoaded` / `OnManualSaveSuccess` / `OnAutoSaveBegin` /
  `OnAutoSaveSuccess` / `OnAutoSaveFail` / `Reset`) として表明することで、
  状態遷移が読みやすくなり、それぞれの文言が正しく出るかをタイマーなしでテストできる。
- `Func<DateTime>` を差し込める設計にしたことで、`SaveStatusText` が正しい時刻文字列を
  含むかも決定論的にテストできる。
- `DispatcherTimer` は WPF スレッドモデルに依存するため `MainViewModel` に残す。
  `CanScheduleAutoSave` プロパティ (`CurrentFilePath あり && _isAutoSaving でない`) を
  公開することで、タイマーを使うかどうかの判断も `MainViewModel` でコンパクトに書ける。
- `SaveState.PropertyChanged` を `MainViewModel` で購読し、`CurrentFilePath` /
  `IsDirty` 変化時に `Title` も再通知することで既存 XAML バインディングを無変更で維持。
- DI コンテナ導入はここでも対象外。`SaveState` は `MainViewModel` のコンストラクタで
  `new` する。

### v0.8.5 で起動導線を 3 つに分けた理由

- 起動処理には性質の異なる責務が混在していた。
  - **純粋ロジック**: 「最近使ったファイル」の追加 / 重複排除 / 5 件上限 / 存在ファイル絞り込み
  - **判断**: 起動引数を見て「直接開く」か「ダイアログを出す」かを決める
  - **UI 状態**: スタートダイアログ上の選択 (`New` / `Open` / `Cancel`) と選ばれたパス
- これらを 1 つの ViewModel に束ねると、純粋ロジックを単体テストするのに WPF 依存や
  ファイルシステム依存が混ざってしまう。
- 役割で 3 つに分けた:
  - `RecentFilesService` — `IEnumerable<string>` → `IReadOnlyList<string>` の純粋関数。
    `Func<string, bool>` を差し込めるため `File.Exists` も置換可能。
  - `StartupCoordinator` — 引数配列 → `StartupAction` レコードの純粋関数。
    旧 `App.OnStartup` と同一の判定ルール (`args[0]` のみ、拡張子フィルタなし) を
    そのまま封じ込める。存在するなら `DirectOpen`、存在しないか引数なしなら `ShowDialog`。
    将来ルールを変えたい場合はこのクラスだけを修正すれば済む。
  - `StartupViewModel` — `Items` / `Choice` / `SelectedPath` を保持する純粋 ViewModel。
    `RecentFileItem` もここに同居させ、`Views` 名前空間からは依存しない。
- `AppSettingsService.AddRecentFile` / `RemoveRecentFile` の公開 API は不変のまま、
  内部だけ `RecentFilesService` に委譲。これにより呼出側 (`MainViewModel.Open` /
  `SaveAs`、`App.OnStartup`) の変更ゼロでロジックだけテスト可能になった。
- `StartupWindow` は引き続きコードビハインドで動かす。MVVM 純粋化のためだけに
  ICommand バインディングへ書き換えるのはコスト過大で、ダイアログのライフサイクル
  (ShowDialog / DialogResult / Close) を VM 側に持たせるのも不自然。XAML は無変更で残す。
- DI コンテナ導入はここでも対象外。`StartupViewModel` は `App.OnStartup` 内で
  `new` され、必要なら `Func<string, bool>` を差し替えるテスト経路のみを開けている。

## なぜカード型 UI にしたか

- 想定するユースケースが「思いつき」「断片」「短文」だから。
- ツリーやアウトラインだと、書く前に **場所を選ぶ判断** が発生してしまう。
  これがアイデアを書き始める初動を遅らせる、というのが NoteNest を運用してきた実感。
- カードの一覧であれば、「とりあえず追加 → あとで探す」が成立する。
- Google Keep のメンタルモデルが広く受け入れられており、初見ユーザーが説明なしで使える。
- ただし Keep の忠実コピーは目指さない。ローカルで完結すること、`.ideanest` 1 ファイルで持ち運べることを優先する。

## なぜ単一 JSON ファイルにしたか

- ユーザーが **自分のファイルとして所有できる** こと、を最も大事にしたい。
- SQLite やキャッシュフォルダだと「アプリが管理する不透明な箱」になり、
  バックアップ・共有・移行が一般職員には難しくなる。
- JSON なら最悪テキストエディタでも読める。これは長期保管にとって重要な特性。
- v0.1.0 は規模が小さい (アイデア数 ≲ 数千) ことを想定しているので、
  JSON 1 ファイルでパフォーマンス上の問題は出ないと判断した。
- バイナリ依存を避けることで、`.bak` による単純な復旧戦略も成立する。

## なぜ画像貼り付けを対象外にしたか

- 単一 JSON ファイルという設計を最優先にした結果、
  バイナリ添付を抱えると JSON が肥大化するか、外部フォルダ参照が必要になる。
- どちらに倒しても「単一ファイルで持ち運べる」が崩れる。
- v0.1.0 の主目的は「素早くテキストを溜める」であり、画像なしで成立する。
- 画像が必要な人は NoteNest 側で扱う前提とする (将来検討)。

## なぜタスク管理を対象外にしたか

- IdeaNest を「期限を持つ仕事の管理」に使い始めると、すぐに NoteNest と機能が重なる。
- 期限・進捗・担当者などを追加した瞬間に **書く前の判断コスト** が増え、
  「思いつきを雑に溜める」というコンセプトが壊れる。
- 期日管理は NoteNest あるいは既存のタスクツールで行う、と境界を明確にした。
- IdeaNest 側は、あくまで「思考の在庫」までを担当する。

## なぜ画面を「カード一覧主役」にしたか (v0.1.2)

- IdeaNest の役割は「思いつきを溜める箱」であり、ユーザーが画面を開いて最初に
  見るべきものは **過去に溜めたカードの一覧** である。
- NoteNest のような「プロジェクト × ツリー × エディタ」型は構造化に強いが、
  カードの俯瞰には不向きで、視線が左ペインや上部メニューに分散する。
- IdeaNest ではカード以外の UI 要素 (枠線・濃いボタン・標準コンボボックスなど)
  をできる限り後退させ、カードを浮き上がらせる構成を取る。
- このため背景を薄いグレー (`#F6F7F9`)、カードを白 + 角丸 + 薄い影で表現し、
  「Google Keep のような軽いボード」というメンタルモデルを優先する。
- ただし Google Keep の見た目を忠実にコピーするわけではない。
  ローカル単一ファイルで完結することを最優先にした上で、その範囲で軽く整える。

## なぜ外部 UI ライブラリを導入しないか (v0.1.2)

- MahApps.Metro / Material Design In XAML / Fluent UI ライブラリなどを入れれば
  見た目は一気に「今っぽく」なるが、依存と学習コストが大きく増える。
- IdeaNest はプロトタイプ規模であり、UI 周りの依存は最小限にしておきたい。
- DLL が増えると自己完結型 (`PublishSingleFile=true`) でも配布物が肥大化する。
- 「カード型ボード」というシンプルな構造であれば、WPF 標準の `Border` /
  `DropShadowEffect` / `ControlTemplate` だけでも、業務画面感を十分に取り除ける。
- 装飾の自由度より、**起動 → 追加 → 検索 → 保存** の素直さを保つことを優先する。

## なぜ機能追加より見た目の整理を優先したか (v0.1.2)

- v0.1.0 / v0.1.1 で「起動 → 追加 → 検索 → 保存 → 読込」の機能は揃った。
- 一方で UI の野暮ったさが、アイデアを見返す体験を阻害していた
  (枠線が多い / カードが平らで読み返したくならない / ボタンが業務画面的)。
- カード型ツールにとっては **「もう一度開きたくなる見た目」** が機能と同じくらい
  重要であり、ここを先に整えないと機能を追加しても使われない。
- そのため v0.1.2 では、機能追加・データ構造変更・保存形式変更は一切行わず、
  視認性と落ち着きだけを底上げした。

## タグ設計の方針 (v0.2.0)

### タグをカードから算出する構造にした理由

タグを独立した DB テーブルや別リストとして管理せず、カードの `Tags` リストから都度算出する設計を採用している。

- `.ideanest` を 1 ファイルで完結させる方針 (タグマスタを別コレクションに持つと JSON 構造が複雑になる)
- カードを削除・編集すれば自動的にタグ一覧が更新される (使われていないタグは自然に消える)
- 将来 v0.x.y で算出コストが問題になる規模 (タグ数 × カード数 が数万) に達した場合はキャッシュ化を検討するが、
  当面は不要と判断した

この設計のため、「未使用タグのクリーンアップ」という操作は不要 — 単純にカードからタグを消せばよい。

### タグ正規化の範囲を最小限にした理由

v0.2.0 でのタグ正規化は「前後空白除去」「先頭 `#` 除去」「空タグ除外」「同一カード内重複排除」のみに留める。

- 大文字小文字の正規化 (`UI` と `ui` を同一視) や全角半角統一は、ユーザーが意図的に使い分けている可能性がある
- v0.1.x 以前のデータを静かに書き換えることへのリスクを避けたい
- 正規化規則が増えると「なぜこのタグが消えたか」がわかりにくくなる

意図した区別が必要な場合は、タグ管理ダイアログでリネームして明示的に統合できる。

この方針に合わせ、タグ一覧の算出 (`RefreshTags`)・タグ絞り込み・タグのリネーム・削除
は すべて `StringComparer.Ordinal` / `StringComparison.Ordinal` で比較する。
`UI` と `ui` は別タグとして扱われ、左ペインにも別行で並ぶ。
一方、検索欄からのキーワード検索 (タイトル / 本文 / タグへの部分一致) は
ユーザーの利便性のため `OrdinalIgnoreCase` のままにしている。
これはタグの同一性判定ではなく、検索ヒットの寛容さなので別ルールで構わない、と判断した。

### タグリネーム = マージとした理由

「リネーム」と「マージ」を別機能として実装する案もあったが、
「リネーム先に既存タグ名を指定したら統合」という 1 つの操作に統一した。

- 操作フローが 1 種類で済む (UI 項目が増えない)
- 「同じ概念を表す 2 つのタグを 1 つにまとめたい」という需要はリネームと本質的に同じ
- タグ管理ダイアログに「マージ先を指定する複数選択 UI」を持つのは v0.2.0 の規模では過剰

## v0.2.3 でクリップボードコピーに Ctrl+C を使わなかった理由

- 現状の実装には「選択中カード」という UI 概念が無い。
  `Ctrl+C` を Window レベルで捕まえると、
  検索欄や他のテキストボックスの通常コピー操作と衝突する。
- `Ctrl+Shift+C` を「表示中カードの一括コピー」に割り当てることで、
  既存ショートカットと衝突せず、意図が明確な操作として機能する。
- カード単体コピーは右クリックメニューで提供し、
  キーボード派には一括コピーショートカットを用意するという分担にした。
- 将来カード選択モデル (クリックで選択状態 + `Ctrl+C` コピー) を導入する場合は、
  `backlog.md` のカード選択モデルと合わせて改めて設計する。

## v0.2.3 の Markdown 整形ロジック共通化について

- v0.2.2 では `MarkdownExportService.Export()` が整形とファイル書き出しを一体で行っていた。
- v0.2.3 では `FormatCard()` (単一カード) と `FormatAll()` (ヘッダー + 全カード) を分離し、
  `Export()` は `FormatAll()` を呼んでファイルに書くだけにした。
- クリップボードコピーはこれらのメソッドを直接呼び出すため、
  出力フォーマットがファイルエクスポートと一致することを保証できる。
- 過度な抽象化を避けるため、テンプレートエンジンや設定可能なフォーマット等は導入しない。

## v0.5.0 画面密度改善の設計方針

### カード一覧を主役にするためにUI密度を下げた理由

- IdeaNest の主目的は「過去に溜めたアイデアを素早く俯瞰する」ことであり、
  検索欄・タグパネル・カード操作ボタンが目立ちすぎるとカード一覧が脇役になる。
- v0.1.2 で確立した「白いカードを浮かび上がらせる」方針を、操作 UI にも一貫して適用した。

### タグパネルを折りたたみ可能にした理由

- タグ一覧は有用だが、常時 200px を占有すると横幅の狭いウィンドウでカードが 1 列になりやすい。
- カードを主軸に使うとき (アイデアを読み返す / エクスポート) はタグパネルが不要なケースがある。
- 折りたたみ状態を `settings.tagPanelOpen` として保存し、開き直してもユーザーの好みを維持できるようにした。
- タグフィルタの選択状態は折りたたみに関係なく維持される。

### カード操作ボタンをホバー時のみ表示にした理由

- 📌 ✎ 📥 🗑 を常時表示すると、カード下部にアイコン行が常に存在し、
  カードの本文・タグよりも操作 UI が目に入りやすくなる。
- WPF の `DataTrigger` + `RelativeSource AncestorType=Border` で、
  マウスが乗っているときのみ Opacity=1 にする実装を採用した。
- Opacity=0 では視覚的に非表示だが DOM には残るため、
  操作中にカードの高さが変わる「レイアウトジャンク」が起きない。
- 右クリックメニューからの操作は常時利用可能としており、
  キーボード派・タッチ環境向けの代替手段を維持している。

### 色チップサイズを 26→22px に縮小した理由

- 検索欄と色フィルタ行の高さを下げる際、26px の丸チップが高さ上の制約になっていた。
- 22px でも 8 色の視覚的な区別は十分に保たれる。

## v0.6.0 カード詳細プレビューの設計方針

### なぜ別ウィンドウ (モーダル) にし、右ペインを採用しなかったか

- 右ペイン常設にすると、カード一覧の横幅が常に圧迫され、v0.5.0 以降「一覧を主役にする」という方針と衝突する。
- カードサイズ S/M/L、タグパネル折りたたみ、検索バーなど既存の横方向 UI 要素と組み合わさると、画面密度の調整が複雑化する。
- モーダルダイアログであれば、見たい瞬間だけ大きく開き、閉じれば即座に一覧主役に戻れる。Google Keep のメンタルモデル (一覧 → タップで開く → 閉じる) とも整合する。

### シングルクリック=プレビュー / 編集はプレビュー経由 にした理由 (v0.6.1 で改訂)

- 「読み返す」と「直す」は IdeaNest 上で頻度が大きく異なる (読み返しの方がはるかに多い)。最も短い操作 (シングルクリック) を読み返しに割り当てるのが自然。
- v0.6.0 ではダブルクリック=編集を残したが、実機で「ダブルクリックするとプレビューと編集が両方開く」体験になり、v0.6.1 でダブルクリック起動を撤去した。導線は **シングルクリック → プレビュー → `✎ 編集` ボタン** に統一する。
- ダブルクリック競合がなくなったため、v0.6.0 で導入した `DispatcherTimer` 280ms 遅延も撤去し、シングルクリックで即時プレビューが開くようになった。
- 編集導線は次のいずれでも維持: プレビュー内の `✎ 編集` ボタン / 一覧ホバーの ✎ ボタン / 右クリック → 編集。
- ホバーボタン (✎ 📌 📥 🗑) からのクリックは `IsInsideButton` で検出し、プレビューを開かない (ボタン自身のコマンドを尊重)。

### プレビュー単体では `IsDirty` を立てない理由

- プレビューは「閲覧専用」と明示することで、ユーザーが安心してカード本文をじっくり読める。
- 編集・ピン留め切替・アーカイブ切替・コピーは既存の `MainViewModel` ハンドラーに委譲しているため、それらが呼ばれた場合は従来どおり `MarkDirty()` が走る。プレビュー側に重複した状態変更ロジックを持たせない。
- 結果として「プレビューを開いて閉じた」だけでは `*` も自動保存も発生しない。誤って大量のカードを開いて閉じても保存ストームを引き起こさない。

### 一覧カード本体に大きく表示せず、別ウィンドウで開く理由

- 一覧の表示密度 (S/M/L) を上げると本文の省略はどうしても発生する。サイズを大きくすれば本文は読みやすくなるが、一覧性 (一画面に何枚見えるか) を犠牲にする。
- 一覧は「俯瞰」、プレビューは「精読」と役割を分けることで、両方のサイズ要件 (一覧は密度優先、プレビューは可読性優先) を別個に最適化できる。
- カード色は背景としてプレビューにも反映し、「どのカードを見ているか」の視覚的連続性を保つ。

## v0.5.2 並び順切替・シャッフル表示の設計方針

### 時系列以外の順で見返す価値

- IdeaNest は「思いついた順に溜める」道具のため、自然と更新日時順 (新しい順) で並べてきた。
- 一方で「過去にどんなアイデアを溜めたか」を再発見する用途では、時系列だけでは古いアイデアが永久に埋もれる。
- タイトル順 (五十音 / アルファベット順での再発見)、作成日時順 (更新で順位が変わらない安定軸)、シャッフル (偶発的な再発見) を選択肢として提供する。

### ランダム表示を「自動シャッフル」ではなく「手動シャッフル」にした理由

- 表示更新のたびに並び順が変わると、ユーザーが「今見ていたカード」を見失い、検索やフィルタ操作の認知負荷が跳ね上がる。
- 一方でランダム表示の価値は「想定外の組み合わせで脳を刺激する」点にあり、頻繁すぎる入替は逆効果。
- 「シャッフルを選択した時点 / 再シャッフルボタンを押した時点でのみ並び順を決める」方式とし、ユーザーが明示的に「混ぜ直したい」と感じたタイミングだけ順序が変わるようにした。
- 検索・タグ・色フィルタを変えても順序は維持されるため、フィルタを切り替えながらシャッフル順の中で対象を絞り込める。

### シャッフル順序を永続化しない理由

- 「シャッフル」は本質的に「偶発性」を提供する機能であり、固定された順序を保存する意味が薄い。
- 保存・復元すると、再起動するたびに同じ「ランダム順」が再現されてしまい、機能としての価値 (毎回違う角度から見返す) が失われる。
- そのため `settings.sortMode` には `"Shuffle"` というモードのみを保存し、開き直したときはその時点で新しくシャッフルする。

### ピン留めカードをシャッフル時も上部固定にした理由

- ピン留めはユーザーが「これは特に大事 / 上に出しておきたい」という優先意思を明示した結果であり、シャッフルの偶発性に飲み込ませるべきではない。
- ピン留めカード内も更新日時順のままにし、シャッフルしない。ピン留めの数は通常少ないため、シャッフルしても得られる視点が小さい一方、「いつも上にあるはずのカードが下に来た」という驚きの方が認知負荷として大きい。

### シャッフル中の新規カードを先頭に挿入する理由

- シャッフル中にカードを追加した場合、追加直後のカードが見えない位置 (末尾) に置かれると、追加した実感が薄れる。
- 既存のシャッフル順序を壊さず、かつユーザーへのフィードバックを優先するため、新規カードのみシャッフル順の先頭に挿入する。
- 再シャッフルボタンを押せば全カードがランダム化されるため、新規カードが先頭に固定され続けることはない。

### 手動並べ替え・ドラッグ操作を v0.5.2 で対象外とした理由

- 手動並べ替えを導入すると、`OrderByPinned ThenByUserDefined ThenBySortMode` といった三段重ねの優先順位が必要になり、ピン留めや並び順切替との関係が複雑化する。
- カードのドラッグ操作には WPF 側の `ListBox` / `ItemsControl` の挙動とのすり合わせや、視覚的なドロップターゲット表示が必要で、v0.5.2 のスコープを超える。
- 「並び替えではなく並び順の選択」という枠で v0.5.2 を区切ることで、既存の `RefreshVisible` の単純なクエリ構造を維持できる。

## v0.5.1 カードサイズ切替の設計方針

### 3 段階サイズ (S/M/L) にした理由

- ユーザーの用途によって最適な密度が異なる。
  アイデアを俯瞰したいときは小 (S)、本文を読みたいときは大 (L)、普段使いは中 (M)。
- 2 段階 (小/大) だと「ちょうど良い中間」が無く、4 段階以上はトグル UI が煩雑になる。
- S: 184×148 / M: 252×212 (従来) / L: 340×280 で、各ステップ約 1.35 倍の面積増。

### カードサイズを文字列型 (`settings.cardSize`) で永続化した理由

- 数値のまま保存すると、将来サイズを調整した際に数値が古い実装を指してしまう。
- 文字列 (`"small"` / `"medium"` / `"large"`) にしておけば、将来の px 調整がユーザーデータに影響しない。
- 読込時に未知値は `"medium"` へフォールバックするため、後方互換性を保てる。

### カードサイズ変更でレイアウトを再計算しない理由

- カード `Border` の `Width`/`Height` を `CardWidth`/`CardHeight` プロパティへバインドするだけで、
  WPF の `WrapPanel` がサイズ変更を自動的にレイアウトに反映する。
- VM 側で `RefreshVisible` を再呼び出す必要はない。

## v0.4.0 自動保存の設計方針

### なぜ自動保存を導入したか

- IdeaNest は「思いついたアイデアを素早く保存する」道具であり、保存忘れによってメモが失われると、ツールとしての信頼が一気に崩れる。
- 一方で「ローカル単一ファイル」「保存先はユーザーが所有する」という設計の前提があるため、勝手に保存先を決めることは避けたい。
- 既に保存先が確定している (`.ideanest` を開いている) 状態でのみ自動保存することで、保存忘れ防止と保存先の自己管理を両立させた。

### 新規未保存状態で自動保存しない理由

- 一時ディレクトリやアプリの隠しフォルダに勝手に書き出すと、ユーザーから見て「自分の `.ideanest` がどこにあるか」がわからなくなる。
- IdeaNest は `.ideanest` をユーザーのファイルとして扱う方針 (`docs/design-decisions.md` の単一 JSON 方針) と矛盾する。
- そのため新規未保存状態では従来どおり手動の `名前を付けて保存` を要求し、最初の保存先決定だけはユーザーに委ねる。

### デバウンス時間を 2 秒にした理由

- 連続入力中に毎タイプ保存すると I/O 過多になり、`.bak` も乱れる。
- 5 秒以上待つと「保存された感」が薄く、自動保存の安心感が損なわれる。
- 体感的には 1〜3 秒が妥当で、中間値の 2 秒を採用した (将来的に設定可能化する余地は残す)。

### `.bak` を自動保存時にも更新する理由

- v0.4.0 では自動保存と手動保存で同じ保存処理 (`WorkspaceService.Save`) を使う。
- 別パスに切り分けると、自動保存と手動保存で挙動が分かれ、運用が複雑になる。
- ただし「自動保存のたびに `.bak` が上書きされる」ため、`.bak` による 1 手戻しの価値は手動保存時に比べて低くなる。
- 世代バックアップや自動保存専用バックアップは将来検討とし、`docs/backlog.md` に残す。

### 保存失敗時に MessageBox を出さない理由

- 自動保存はバックグラウンド動作であり、毎回モーダルダイアログが出ると編集体験が壊れる。
- 失敗は `SaveStatusText` (`自動保存に失敗しました`) とタイトルバーの `*` で示し、ユーザーが任意のタイミングで対処できるようにした。
- 終了時には `ConfirmDiscardChanges` が動作するため、失敗状態のまま閉じようとすると確認ダイアログで気付ける。

### 終了時確認を自動保存済みの場合に省く理由

- 自動保存が完了し `IsDirty == false` の状態では失うものがないため、確認ダイアログは不要。
- 自動保存失敗で `IsDirty == true` のまま、または新規未保存状態で変更がある場合は従来どおり確認を出す。

## v0.3.1 NoteNest 向け出力オプションの設計方針

### オプションを設定に保存せずダイアログ毎回表示にした理由

- NoteNest へ渡すアイデアのセット・目的は実行のたびに変わる可能性があるため、
  オプションを永続化するより毎回確認させるほうが誤出力を防ぐ。
- 操作フローとして「出力対象 0 件なら即メッセージ → 0 件でなければオプションダイアログ → ファイルまたはクリップボード」
  とすることで、余計なダイアログを最小限に抑えつつ意図を確認できる。

### `[TODO]` の初期値を OFF にした理由

- `[TODO]` を全カードに付けると NoteNest 側のマーカー一覧が増えすぎる。
- 「移行したアイデア」を示す `[NOTE]` は常に有用だが、
  「採用判断」を示す `[TODO]` はユーザーが意識的に選びたいタスクにのみ付けるべきである。
- 初期値 OFF にすることで、意識せずに使ったとき (デフォルト動作) でも過剰なマーカーが生まれない。

### 出力プレビューを v0.3.1 に含めなかった理由

- オプション変更の即時プレビューには ScrollViewer + テキスト生成が必要で、
  ダイアログの複雑さが増す割に、ファイルまたはクリップボードで確認できるため実用上は不要。
- `docs/backlog.md` に将来検討として残す。

## v0.3.0 NoteNest 向けエクスポートの設計方針

### `.notenest` 直接生成ではなくテキスト出力に留めた理由

- NoteNest の内部 JSON 構造 (`.notenest`) に依存すると、NoteNest 側の仕様変更が IdeaNest に波及する。
  IdeaNest は NoteNest の実装詳細を知るべき位置にない。
- テキスト出力 → NoteNest への貼り付けという手順はユーザーが介在し、
  「どのプロジェクトに入れるか」「採用判断をどうするか」をユーザー自身が決められる。
  直接書き込みでは誤って追記した場合のリカバリが困難になる。
- 将来的に連携を強化する場合は NoteNest 側でインポート機能を設けるほうが責務が明確。

### NoteNest マーカー記法 (`[NOTE]` `[TODO]`) を活用する理由

- NoteNest では本文中の `[TODO]` `[FIXME]` `[NOTE]` を構造化マーカーとして扱えるため、
  移行後にそのまま NoteNest の機能 (マーカー一覧・検索) で扱えるようになる。
- IdeaNest 側では固定の「移行アイデア」「採用判断」マーカーを付与することで、
  NoteNest 内での作業進捗 (採用 / 不採用 / 検討中) をマーカー管理に乗せられる。
- 将来的にマーカー文言を選択式にする拡張に備え、定数を `NoteNestExportService` 内にまとめ、
  コード各所に文字列を散在させない設計にした。

### `MarkdownExportService.ColorDisplayName` を NoteNest 側で共用する理由

- 色の日本語表示名 (黄 / 青 / 緑 など) はアプリ全体で統一すべき語彙であり、
  サービスごとに別々のマップを持つと定義が分散して更新漏れが起きる。
- `ColorDisplayName` を `public static` にしてクロスサービスで参照することで、
  表示名の変更が 1 箇所で完結する。

## v0.2.2 で NoteNest 専用連携より汎用 Markdown エクスポートを先に実装した理由

- IdeaNest に溜めたアイデアの活用先は NoteNest に限らない。
  Markdown エディタ・記事下書き・設計メモ・プロンプト作成など多様であり、
  最初から NoteNest 専用フォーマットに縛ると汎用性が失われる。
- `.ideanest` は「ローカルで所有・保管するデータ形式」、
  Markdown エクスポートは「外部ツールで活用するための書き出し」と役割を分ける。
  両者は独立しており、エクスポートが `.ideanest` の構造に影響しない。
- 再インポート (`.md` → `.ideanest`) は v0.2.2 の対象外。
  IdeaNest の役割は「思考の在庫」であり、
  インポート機能が必要になるのは別ツールとの連携フローが確立してからでよい。
- NoteNest 向けエクスポートは将来 v0.3.0 以降で個別に検討する。
  Markdown エクスポートで共通部分 (フィルタ反映・UTF-8・出力順) の設計を先に固める。

## なぜカード高さを「固定」と「本文に合わせる」のモード切替にしたか (v0.7.2)

- 固定高さは一覧の整然さを生むが、短文カードでも縦に同じ枠を取るため、
  全体を俯瞰する密度が落ちる。一方、本文に合わせる方式 (Auto) は密度を上げられるが、
  並びが不揃いで「整理されたボード感」を損なうユースケースもある。
- どちらかに倒すと別のユースケースが犠牲になるため、表示モードとして両立させた。
  既定は従来挙動と一致する「固定」とし、既存ユーザーに変化を強いない。
- 可変モードでも S / M / L ごとに最小・最大高さを設定し、極端に低い / 高いカードが
  並ばないようにした。最大高さを超える本文は `ClipToBounds` で省略表示し、
  全文はカード詳細プレビュー (v0.6.0) または編集ダイアログから確認できる、
  という既存導線で十分とみなしている。
- Masonry レイアウトやカードごとの個別サイズ指定は今回見送り。
  WPF の `WrapPanel` で素直に表現でき、追加の依存も発生しない範囲に留めた。

## なぜ高さ可変カードに `VerticalAlignment="Top"` を明示したか (v0.7.3)

- WPF の `WrapPanel`(Horizontal) は各行の行高さを「その行の最大子要素 DesiredSize.Height」に揃えたうえで、
  子要素の `VerticalAlignment` に従って Arrange する。Border の既定 `VerticalAlignment` は `Stretch` のため、
  v0.7.2 の「本文に合わせる」モードでは短文カードでも行内の長文カードと同じ高さまで自動で引き伸ばされていた。
- これは Auto モードの「本文量に応じてカードごとに高さが変わる」という意図に反するため、
  カード Border に `VerticalAlignment="Top"` を明示して、自身が要求した DesiredSize を保つよう修正した。
- 固定モードでは Border に明示的な `Height` が与えられており、`VerticalAlignment` の値はサイズ決定に
  影響しないため、固定モードの見た目には変化がない。
- 完全な Masonry (短文カードの直下に次行のカードを詰めて配置する) は引き続きスコープ外とし、
  行内の高さばらつきだけを許容する形に留める。完全な Masonry が必要になった場合は
  カスタム `Panel` の実装が要るため、backlog で別途検討する。

## なぜ Unit Test プロジェクトを `net8.0` + `<Compile Include>` 構成にしたか (v0.8.0)

- 本体 `IdeaNest` は WPF を使うため `net8.0-windows` をターゲットとしており、
  プロジェクト参照 (`<ProjectReference>`) を行うと、テストプロジェクトも
  Windows 専用になり、Linux / macOS / CI コンテナで `dotnet test` を実行できなくなる。
- 一方、テストしたいロジック (タグ正規化、`WorkspaceService`、エクスポート、
  カード表示計算など) は WPF 非依存で、すでに `tools/IdeaNest.Smoke` が
  `<Compile Include>` で同じファイルをリンクしてクロスプラットフォームに動かしている。
- そこで `IdeaNest.Tests` も同じ方針を採用。`TargetFramework=net8.0`、
  `<ProjectReference>` 無し、必要なソースだけ `<Compile Include>` でリンクする。
  これで Linux でも `dotnet test` が走り、`MainViewModel` を分割する際の
  安全網として機能する。
- 代償として「テストに登場するクラスを増やすたびに `csproj` の `<Compile Include>`
  を追記する必要」が生じるが、追加コストは小さく、テスト対象が WPF に
  侵食されるのを抑える効果のほうが大きい。
- `xUnit` を選んだのは `.NET 8` テンプレートの既定であり、追加学習コストが
  低いため。MSTest / NUnit を選ぶ強い理由は今回はない。
- 将来 `MainViewModel` を分割した結果として WPF 非依存のサブ ViewModel が
  生まれたら、同じ `<Compile Include>` リストに追加してテストを足していけば
  そのまま運用できる。

## IdeaNest / NoteNest 疎結合方針 (v1.0.4)

### テキスト形式を共通インターフェースとする理由

- IdeaNest と NoteNest は **独立したリリースサイクル** を持つ別ツールであり、
  どちらかのスキーマ変更がもう一方に波及しない設計を保つことが最優先。
- `.notenest` への直接書き込みや `.ideanest` ↔ `.notenest` 変換ツールを提供すると、
  スキーマ依存が生まれ、どちらかの内部構造を変えるたびに両アプリの更新が必要になる。
- テキスト出力 (NoteNest 向けエクスポート) を介することで、
  「どのプロジェクトに入れるか」をユーザーが NoteNest 側で自由に決められ、
  誤追記のリカバリも容易になる。
- この方針は v0.3.0 の設計判断 (「`.notenest` 直接生成ではなくテキスト出力に留めた理由」) から
  一貫して維持している。

### 連携を「強化」する場合の責務の置き場所

- 将来連携を深めるなら、**NoteNest 側にインポートコマンドを設ける**のが正しい方向。
  IdeaNest は「移行データを作る役割」、NoteNest は「受け取る役割」と分担が明確になる。
- IdeaNest 側が NoteNest の内部構造を知るべきではなく、逆方向も同様。
  知識を片方に押し込めることで、もう片方の設計変更が自由になる。

### 共通化を急がない理由

- タグ正規化・Markdown 整形・JSON スキーマ管理などは各アプリに実装があるが、
  共通ライブラリ化のコストは現時点で利点を上回る。
- 「コードの重複を避ける」よりも「デプロイ単位を独立させる」ことを優先する段階。
- 将来両ツールのスキーマが安定し、共通仕様を先に合意できたなら、
  共通ライブラリや NestSuite 構想の実装コストが下がる。逆順にしない。
- 詳細な候補一覧と「今やらないこと」は `docs/integration-notenest.md` に記録した。

## なぜ NoteNest とは別ツールにしたか

- 同じアプリの中に「腰を据えて書く画面」と「雑に溜める画面」を同居させると、
  どちらの UI も中途半端になりやすい。
- 起動時にモード選択を強いるのも、初動コストを上げてしまう。
- 別アプリにすることで、ショートカット起動でそれぞれを最短距離で使える。
- データも `.notenest` / `.ideanest` で完全に分離でき、
  片方が壊れてももう片方に波及しない。
- 将来 NoteNest 向けエクスポートを足すとしても、それは橋渡しであり同居ではない。
