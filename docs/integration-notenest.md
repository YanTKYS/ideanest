# IdeaNest / NoteNest 連携設計メモ

このドキュメントは「IdeaNest と NoteNest がどう共存するか」の設計方針と、
今後の連携強化を検討するための参照資料です。
コードの実装詳細ではなく、**ツール間の境界と連携フローの考え方** を記録します。

---

## 役割分担

| 観点 | IdeaNest | NoteNest |
| --- | --- | --- |
| 主目的 | アイデアの即時メモと検索 | プロジェクト管理・ノート管理 |
| 主単位 | カード (短文) | プロジェクト / ノート |
| 書くタイミング | パッと書く (発散) | じっくり書く (収束) |
| 整理の深さ | タグ・色のみ (浅い) | ツリー・マーカー・タスク (深い) |
| ファイル形式 | `.ideanest` (JSON) | `.notenest` (JSON) |
| 想定スコープ | 「思考の在庫」 | 「実行中の仕事」 |

IdeaNest は NoteNest の縮小版でも下書きエリアでもない。  
「雑に溜める → 後で探す → 必要なものを NoteNest に移す」という**フロー**の最初の受け皿として機能する。

---

## 現在の連携フロー (v1.0.x)

```
IdeaNest (溜める)
  ↓
NoteNest向けエクスポート (ファイル → エクスポート → NoteNest向けテキスト...)
  ↓
テキストファイル (.txt) または クリップボード
  ↓
NoteNest (貼り付け / インポート) ← ユーザーが手動で実施
```

### エクスポート時のオプション

- `[NOTE]` マーカー付与 (常時 ON 推奨)
- `[TODO]` マーカー付与 (デフォルト OFF)
- タグ / 色 / 日時メタデータの出力有無
- 対象: 現在表示中 (フィルタ適用後) のカードのみ

### 設計上の制約 (意図的なもの)

- IdeaNest は NoteNest の **内部 JSON 構造 (`.notenest`)** を直接生成しない。
  NoteNest 側の仕様変更が IdeaNest に波及するリスクを避けるため。
- テキスト出力を介することで、ユーザーが「どのプロジェクトに入れるか」を
  NoteNest 側で決められる。直接書き込みでは誤追記のリカバリが難しい。
- 将来連携を強化するなら、NoteNest 側にインポートコマンドを設けるほうが責務が明確
  (`docs/backlog.md` の H4 参照)。

---

## `.ideanest` / `.notenest` ファイルの非変換方針

- `.ideanest` → `.notenest` の **直接変換ツールは現時点では提供しない**。
  - 両形式の JSON スキーマは独立して進化できる必要がある。
  - 変換ツールを提供すると、どちらかのスキーマ変更時に変換ロジックの維持コストが発生する。
- `.notenest` → `.ideanest` の逆方向変換も同様の理由で提供しない。
- 「橋渡し」はテキスト (Markdown / NoteNest向けテキスト) 形式を介することで、
  両ツールの独立性を保つ。

## 将来の連携強化候補

以下は将来検討するアイデアの整理です。現時点では実装しません。
優先度・スコープ・工数は `docs/backlog.md` の該当項目を参照してください。

### NoteNest 側インポート機能 (バックログ H4)

- NoteNest 側に「IdeaNest から移行」コマンドを追加する。
- IdeaNest が出力した NoteNest 向けテキストを NoteNest が解析し、
  プロジェクト・ノートとして取り込む。
- IdeaNest 単体では実現不可 (NoteNest リポジトリの改修が必要)。

### 共通設定・共通ランチャー (NestSuite 構想)

- IdeaNest / NoteNest を同じランチャーから起動し、最近使ったファイルを
  統合して表示するアプリケーション群のフレームワーク。
- アプリ間でカラーパレット・ショートカットキー体系・フォントサイズなどの
  設定を共有できる可能性がある。
- ただし、現時点では両ツールの独立性を優先し、共通化は段階的に検討する
  (`docs/backlog.md` の「NestSuite / ランチャー」セクション参照)。

## 処理ロジックの共通化可能性

IdeaNest と NoteNest は現在それぞれに JSON 読み書き・タグ正規化・
Markdown 整形などのロジックを持っている。以下は将来の共通化を検討できる領域。

| 処理 | 現状 | 共通化の判断 |
| --- | --- | --- |
| タグ正規化 (前後空白・`#` 除去・重複排除) | 各アプリに実装 | ロジックは同じだが、共通ライブラリ化のコスト > メリット (今は見送り) |
| Markdown 整形 | 各アプリに実装 | フォーマット仕様が異なるため共通化は難しい |
| `[NOTE]` / `[TODO]` マーカー記法 | IdeaNest 側で定数化 | NoteNest 側がこれを「公式フォーマット」として認識する仕様を合わせるほうが本質的 |
| JSON スキーマバージョン管理 | 未実装 (backlog M6) | 共通ライブラリ化よりも各アプリが独立して行うほうが現実的 |
| 色パレット定義 | 各アプリに実装 | 将来 H2 (ユーザー定義カラーパレット) を実装する際に再検討 |

**現時点の方針**: 共通ライブラリを作るより、**インターフェース (テキスト形式)** を共通仕様として明確化するほうが、両ツールの独立リリースサイクルを妨げない。

## NestSuite / ランチャー構想の整理

「IdeaNest と NoteNest をまとめて管理するランチャー / ハブアプリ」というアイデアは
長期的には検討対象ですが、現時点では実装しません。

### 実現するなら必要な判断

1. **アプリ間の設定共有**: `settings.json` を別フォルダに持つ 2 つのアプリが
   どうやって共通設定を参照するか (共通設定ファイルの置き場所と形式)。
2. **ランチャーの UI**: 最近使ったファイルを統合するだけか、プロジェクト一覧なども出すか。
3. **依存の方向**: IdeaNest / NoteNest がランチャーに依存するか、ランチャーが両者を起動するだけか。
4. **リリースサイクル**: ランチャーを別リポジトリにするか、NoteNest に同梱するか。

### 今やらない理由

- 現時点では「まず各ツールの単体完成度を上げる」ことが優先。
- ランチャーを導入すると、インストール・アップデートの単位が増え、ユーザーへの説明コストも増える。
- IdeaNest の「単一 `.ideanest` ファイルで完結・持ち運べる」という設計哲学と、
  複数アプリ間で設定を共有するハブ型アーキテクチャは一部矛盾する。

---

## 今の段階でやらないこと

以下は連携に関して「価値はわかるが現時点では実装しない」と判断している項目です。
なぜやらないかを明確にしておくことで、将来の判断を楽にします。

| 項目 | 理由 |
| --- | --- |
| `.notenest` への直接書き込み | スキーマ依存・誤追記リスク・NoteNest 側で受け口を設けるほうが責務が明確 |
| `.ideanest` ↔ `.notenest` 変換ツール | スキーマが独立進化する前提と矛盾。将来スキーマが安定したら再検討 |
| NoteNest のプロジェクト一覧を IdeaNest 内に表示 | 「フラット一覧のアイデアボード」というコンセプトを逸脱する |
| IdeaNest カードの「移動済み」フラグ | どのプロジェクトに移したかを追跡する機能は NoteNest 側の責務 |
| 共通ランチャー / NestSuite | 単体完成度が優先。ランチャーは両ツールが成熟してから検討 |
| リアルタイム同期 / Watch フォルダ | ローカル単一ファイル方針と、常駐プロセスを持たない設計と合わない |
